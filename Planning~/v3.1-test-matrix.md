# v3.1 — Editor Live Microphone Test Matrix

v3.1 (shipped as 0.11.0) adds a live-microphone backend inside the Unity
Editor on Windows. `VoskSpeechRecogniser.StartRecognition()` transparently
auto-routes to a managed `EditorMicBackend` that captures audio via
`UnityEngine.Microphone`, runs it through C# ports of the existing 48→16 kHz
downsampler and AGC, and feeds int16 PCM directly to `libvosk.dll` via
P/Invoke. No public API changed, and the Android native path is untouched.

This matrix has three halves:

1. **Phases 0–1: Automated coverage.** Editor-mode DSP tests for the new
   `Downsampler.cs` and `Agc.cs` ports, plus regression runs of every
   suite carried over from v3.0.
2. **Phases 2–7: Windows Editor live-mic verification.** Smoke tests,
   error paths, lifecycle robustness, and end-to-end recognition using a
   headset microphone plugged into the Windows host (e.g. Quest Link,
   Index, USB headset).
3. **Phases 8–10: Quest 3 regression + build verification.** Confirms
   v3.1 did not break the Android path — the existing v2.5 / v3.0 on-device
   behaviour must continue to work unchanged, and the Android build must
   not accidentally ship the Windows DLLs.

## Prerequisites

### Common

1. **Consuming project**: `D:\Game Development\voxsdk` (per
   `reference_unity_test_project.md`) — the package is referenced via
   `file:` and `manifest.json` already has
   `"testables": ["com.jinwoo1601.vosk-xr"]`.
2. **Unity 6000.3.7f1** (matches the Android toolchain pinned in
   `CLAUDE.md`).

### Windows Editor phases (2–7)

3. **VOSK Windows runtime** present under `Runtime/Plugins/x86_64/`:
   `libvosk.dll`, `libgcc_s_seh-1.dll`, `libstdc++-6.dll`,
   `libwinpthread-1.dll`. Download from
   https://github.com/alphacep/vosk-api/releases (see
   `v3.1-editor-mic-plan.md` for instructions).
4. **Plugin importer flags** on each DLL configured for Editor / Windows
   x86_64 only — explicitly excluded from Android, Standalone Win64,
   Linux, macOS.
5. **Headset microphone** connected to the Windows host and set as the
   Windows default recording device (Settings → System → Sound → Input).
   The v3.1 backend calls `Microphone.Start(null, ...)` which binds to
   Unity's default device, which follows the Windows default. Any of the
   following counts as a "headset mic" for the purposes of this matrix:
    - **Quest 3 via Quest Link / Air Link** (USB-C or Wi-Fi to the PC) —
      the headset microphone appears as a normal Windows input device
      named `Headset Microphone (Oculus Virtual Audio Device)`.
    - **Valve Index / Vive Pro / Varjo** built-in mic over USB.
    - **Any USB or 3.5 mm headset** (gaming headset, boom mic, etc.) —
      behaviour is equivalent; v3.1 does not know about VR specifically.
6. **Windows microphone permission** granted at OS level: Settings →
   Privacy & security → Microphone → "Let apps access your microphone"
   ON, and the desktop-apps toggle ON. Unity does not trigger this
   dialog automatically; a revoked permission surfaces as silent audio
   in row 2.1.

### Quest 3 phases (8–10)

7. **Quest 3** connected via USB with `adb` reachable from WSL using the
   path in `CLAUDE.md`. Developer mode enabled, app installed from a
   Unity Android build of the consuming project.
8. **NativeBridge built**: `libvosk-bridge.so` + `libvosk.so` present
   under `Runtime/Plugins/Android/arm64-v8a/`. See `CLAUDE.md` for the
   cmake build command.
9. **No `libvosk.dll` in the APK.** Checked as Phase 10 build-integrity
   verification.

## Driver snippets

### Phase 2–6 live-mic driver

The `CommandRecognition` sample already wires a `VoskSpeechRecogniser` +
`VoskCommandRecogniser` + `CommandDemo`, so the sample scene is the
live-mic harness — no extra script is required. The only additions for
this matrix are optional diagnostic logs. Drop this helper into
`Assets/` in the consuming project and attach to the same GameObject as
`VoskSpeechRecogniser` to surface microphone state in the Console:

```csharp
using UnityEngine;
using VoskXR;

public class V31EditorMicDiagnostic : MonoBehaviour
{
    [SerializeField] VoskSpeechRecogniser speech;

    void OnEnable()
    {
        speech.OnPartialResult += p => Debug.Log($"[Partial] \"{p}\"");
        speech.OnFinalResult   += f => Debug.Log($"[Final]   \"{f}\"");
        speech.OnError         += (code, msg) =>
            Debug.LogError($"[VoskError] {code}: {msg}");
        speech.OnModelReady    += () => Debug.Log("[Model] ready");
    }

    void Start()
    {
        Debug.Log($"[Mic] devices={string.Join(", ", Microphone.devices)}");
    }
}
```

## Phase 6: Windows Editor — Lifecycle / Domain Reload

Phase 0 counts each suite as a row; the underlying test count is 172

### What this matrix proves

- **Editor path works.** Phases 2–6 prove `libvosk.dll` loads, the
  C# Downsampler + AGC produce usable audio for VOSK, and the full
  event surface (`OnPartialResult`, `OnFinalResult`, `OnResult`, `OnError`)
  behaves identically to the Android path.
- **Headset mic works.** Phase 3 + Phase 4 specifically exercise a
  headset microphone (Quest Link, Index, USB gaming headset) as the
  Windows default input, which is the v3.1 developer-iteration use case.
- **Android path is unbroken.** Phases 8–10 confirm v3.1's additions
  are invisible on Quest 3 at runtime and at build time — no new
  symbols in the APK, no behaviour drift.
- **Transparent routing is transparent.** Phase 7 + Phase 9 prove that
  the exact same `VoskSpeechRecogniser` + `VoskCommandRecogniser` code
  in the sample scene and in user scripts works unchanged on both
  platforms — which is the entire v3.1 design promise.

### What this matrix does NOT cover

- **Standalone Windows build runtime**. Phase 10.4 is a build-only
  canary. Real PCVR runtime support is deferred to a future version
  per the scope decision in `v3-and-beyond-analysis.md` /
  `v3.1-editor-mic-plan.md`. That future version gets its own matrix.
- **macOS / Linux Editor.** Unsupported; `#if UNITY_EDITOR_WIN` guards
  exclude them. The Microphone and libvosk paths are never compiled on
  those hosts, and there's nothing to test.
- **Non-headset PC microphones.** A laptop's internal array mic or a
  desk condenser will generally work the same way, but v3.1 targets
  the headset-mic use case (developer wearing the HMD while iterating,
  or testing with the PCVR mic without the headset on). Non-headset
  PC mics are covered incidentally by Phase 3 if used.
- **Sample-rate resampling.** v3.1 hard-requires 48 kHz input from
  `UnityEngine.Microphone`. Row 5.3 checks the guard; a rational-ratio
  resampler for 44.1 kHz is a deferred PCVR-version item.
- **Multi-mic device selection**. `Microphone.Start(null, ...)` binds
  to the Windows default. Switching between a headset mic and a
  built-in mic mid-session is not supported in v3.1 — `Microphone.SetInputDevice`
  passthrough is a deferred PCVR-version item.

If you're iterating on **command definitions, acoustic thresholds, or
anything you can hear**, this matrix plus the Editor live-mic path is
sufficient before tagging a release. If you're adding a PCVR runtime
build target, this matrix is necessary but not sufficient — expand
Phase 10 into a real standalone-build phase and add per-headset device
coverage.
