# v1.1 Improvement Plan

Identified issues from v1.0 review, analysed in detail.

## Critical (correctness/stability)

### ~~1. Data race on `g_last_partial`~~ — FALSE POSITIVE
**File:** `NativeBridge~/src/vosk_bridge.cpp`  
On closer analysis, this is safe. `reset_pipeline()` (the only other accessor) is always called either before the recognition thread starts or after `join()`. The `std::thread` constructor and `join()` provide the necessary happens-before guarantees. No fix needed.

### ~~2. `g_last_error` race~~ — FALSE POSITIVE
**Files:** `NativeBridge~/src/vosk_bridge.cpp`, `Runtime/Native/BridgeNative.cs`  
On closer analysis, this is safe. The recognition thread never touches `g_last_error` — it reports errors through the mutex-protected `ResultQueue` instead. All `g_last_error` reads and writes happen in the `extern "C"` API functions, which are only called from Unity's main thread. The static `ErrorBuf` in C# is likewise only accessed from the main thread. No fix needed.

### ~~3. `_initialising` flag not reset on early-return paths~~ — FALSE POSITIVE
**File:** `Runtime/VoskSpeechRecogniser.cs`  
The code already has a `finally` block (line 85-88) that resets `_initialising = false`. In C#, `finally` runs on all exit paths including `return` inside `try`. The flag is correctly reset whether extraction fails, init fails, or an exception is thrown. No fix needed.

## Important (robustness)

### 4. Hardcoded mic gain (3.0x) — REAL, LOW URGENCY
**File:** `NativeBridge~/src/vosk_bridge.cpp:40`, used at lines 91-96  
The 3x gain is tuned for Quest 3's quiet mic. Clamping to [-1,1] prevents overflow, so the worst case on a louder device is clipping distortion, not a crash. Not a problem today since we only target Quest 3. Becomes important when adding support for other headsets (Pico, Apple Vision Pro, etc.) that may output full-range audio.  
**Fix:** Add `float micGain` parameter to `vosk_bridge_init()`, store in a static, expose as `[SerializeField]` on the C# side.

### ~~5. Hardcoded audio params~~ — DEFER TO v2.0
**File:** `NativeBridge~/src/audio_capture_audiorecord.cpp:10-13`  
The 48 kHz rate cascades through the entire pipeline: the downsampler's decimation factor (3 = 48/16), FIR coefficients (designed for 48 kHz), ring buffer sizing, and read chunk size are all tuned to it. Making sample rate truly configurable requires replacing the integer-ratio FIR downsampler with a general-purpose resampler — that's an architectural change, not a parameter swap. The current design is correct for its target hardware.

### 6. Unbounded result queue — REAL, LOW SEVERITY
**File:** `NativeBridge~/src/result_queue.h`  
Memory risk is negligible (~24 KB/minute of unpolled results). The real issue is stale result flooding: if C# stops polling (scene transition, backgrounded app) and resumes, `Update()` drains the entire backlog in one frame — potentially hundreds of `OnPartialResult` events causing a frame spike.  
**Fix:** Cap the deque at ~64 entries, evicting oldest partials (never evict finals).

### 7. No JNI exception checks in ReadLoop — REAL BUG
**File:** `NativeBridge~/src/audio_capture_audiorecord.cpp:180-181`  
After `CallIntMethod` for `AudioRecord.read()`, there is no `ExceptionCheck()`. If `read()` throws (e.g. `IllegalStateException` from OS reclaiming the audio device while backgrounded), the JNI exception flag stays set. The next JNI call — `GetFloatArrayElements` on line 192 — will return null or crash the VM. Dereferencing that null pointer would segfault. Compare with `Start()`, which correctly checks exceptions after `NewObject` (line 88) and `startRecording` (line 113).  
**Fix:** Add `ExceptionCheck`/`ExceptionClear` after `CallIntMethod` in the read loop. ~5 lines.

## Quality-of-life

### ~~8. Manual JSON parsing~~ — OVERSTATED, KEEP AS-IS
**File:** `Runtime/VoskSpeechRecogniser.cs:298-326`  
VOSK's output is always a single flat object with one key (`"text"` or `"partial"`). The manual parser correctly handles this including escaped quotes/backslashes, has zero dependencies, and minimal allocations. `JsonUtility` would require a `[Serializable]` class + reflection overhead; `SimpleJSON` adds a file dependency. Neither buys much for a single-key JSON object. Revisit when adding new data fields (confidence, timestamps), not before.

### 9. No progress callback for model extraction — NICE-TO-HAVE
**File:** `Runtime/ModelExtractor.cs:47-78`  
The small models we currently ship (~40 MB) extract in 2-5 seconds on Quest 3, and only on first launch (subsequent runs hit the cache at line 27-30). For the current scope this is barely noticeable. Would matter for models >200 MB, but shipping models that large on mobile XR is impractical. Low priority unless model sizes grow.

### ~~10. No disk space check before extraction~~ — FALSE ALARM
**File:** `Runtime/ModelExtractor.cs`  
Overstated as "silently corrupts." In reality: if disk space runs out, `ExtractToFile` throws `IOException`, caught by the outer catch (line 94), which deletes the temp directory (line 98-99) and reports via `onError` (line 106-107). The atomic rename never happens. No corruption. A pre-check would give a nicer error message with specific numbers, but the existing error handling is correct.

### 11. Build improvements — REAL, EASY WIN
**File:** `NativeBridge~/CMakeLists.txt`  
Three low-risk, one-line additions:
- **`-fvisibility=hidden`** — hides internal symbols (`recognition_loop`, `reset_pipeline`, etc.) from the export table. Only `extern "C"` functions remain visible. Prevents ABI leaks and enables better compiler optimisation of internal calls.
- **`-flto`** — link-time optimisation. Enables cross-TU inlining of hot paths (downsampler, ring buffer).
- **`-s` / `--strip-all`** — strip debug symbols from release builds. Current binary is 445 KB; expect ~30-50% reduction.
