## [Unreleased]

### Added

- **The Editor now tells you when a grammar word is not in the model's vocabulary, instead of letting the decoder drop it silently.** A word VOSK has never heard of cannot be recognised — the decoder discards it when the grammar is compiled, and the Kaldi-side complaint is suppressed by the log level the bridge sets, so the only symptom was a phrase that never matched and a transcript that gave no reason. Whenever a grammar is handed to the model, every word it contains is now looked up with `vosk_model_find_word`, and each unknown word logs one Console warning naming it and repeating the two documented remedies (spell the phrase out in the slot value, or add a phonetic alias). Because the check runs at the point where a grammar meets a live model handle rather than where the grammar is generated, it also covers runtime rebuilds — a `SetActiveSets` switch, or an explicit `RebuildGrammar()` — and it does not misfire on the common startup ordering where the grammar is built before the model has finished loading. It never rejects a grammar: the grammar is applied exactly as before and nothing about parsing, scoring, or which commands fire moves. The package's own `[unk]` token is skipped deliberately, since it is not author vocabulary. **Windows Editor only** (`UNITY_EDITOR_WIN`, because the managed libvosk bindings exist only there, and `[Conditional("UNITY_EDITOR")]` besides) — player builds and non-Windows Editors are unchanged, and no public API is added. Pointed at the shipped sample grammar the check surfaces two words: `cqb`, which `KNOWN_LIMITATIONS.md` already documented, and `railgun`, which nothing in the repo had recorded. ([#143](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/143))

## [2.0.0] - 2026-08-28

### Changed

- **Breaking (behaviour) — a command whose first required element was never heard no longer fires.** Say "time to target track one two four four" at a grammar holding `query_time_to_target : ["time","to","target"]` and `intercept_target : ["intercept","track","{track}"]`, and until now VoXR fired **two** commands: the query you asked for at `1.00`, and `intercept_target` at `0.67` — with the word "intercept" never spoken. A read-only query executed a manoeuvre order, and nothing marked the second command as invented: every token decoded cleanly, so the per-word confidence table was spotless, and `OnCommandRecognised` fires once per command, so a subscriber could not tell the two came from one utterance. From this release a candidate whose **first required element matched nothing** may still compete and still consume the words it matched, but it may not produce a result. In a command grammar that first element is the **verb** — what to *do* — while the elements after it are arguments — what to do it *to*. Losing an argument still leaves the action identified, and the score reports the damage; losing the verb leaves no evidence that any action was requested at all, only that some words happened to match a pattern's tail. That difference is positional, and no threshold can express it: `minScore` sees `2/3` and cannot ask *which* third went missing. **No score changes and no scoring constant moves** — every command that fires carries exactly the score it carried before. What changes is whether an already-computed score is allowed to produce a result. The phenomenon is wider than the reported case: the same phantom fires **standalone, in round 1**, with no first command present ("track one two four four" alone fired `intercept_target`), so at any `bufferWindow` a pause longer than the window delivered a tail exactly like this — which is why the rule is not scoped to "the second command in an utterance". **What this costs you**, stated plainly: where the leading word *was* spoken and the decoder dropped it, VoXR used to recover the command and now reports nothing, so the speaker re-utters. There is no transcript-level discriminator between "never spoken" and "spoken and lost" — acoustic-gap timing and `[unk]` evidence were both tested against field recordings and neither separates the two — so an unrecoverable wrong action is traded for a recoverable "didn't catch that". Measured across a 699-utterance corpus built to contain both: 48 rows change, 17 fire nothing where they previously fired something, and **zero commands scoring a clean `1.00` are lost**. A barred candidate still **consumes** the words it matched, and that is load-bearing rather than incidental: it re-bases the search past leading debris, so "target hotel one cease fire" still gives you `cease_fire` at `1.00` instead of charging it for three unexplained leading words and sinking it below the gate. Utterances that now produce nothing arrive as `OnUnrecognisedSpeech`, exactly as any other unmatched speech does — there is no new event, no new reject reason, and no new enum value. The rule also applies on the **eager-commit** path, so an affected utterance waits for the buffer window instead of firing early and is then refused at the flush; it never fires either way. It applies uniformly whether the anchor is a literal or a slot, it is unconditional and on by default, and it adds **no** public API: no new field, constructor parameter, event, or changed signature, so integrator code compiles and links unchanged. Everything downstream that was fed by such a command goes quiet with it, which is the intended subtraction but is worth enumerating: a command that opted into `allowPartialMatch` no longer opens a slot-fill prompt when its verb is missing (there is no command to hold open), one marked `requiresConfirmation` no longer asks you to confirm an action nobody requested, and with `disambiguateSiblingTies` set, a tie between two commands that both lost their leading word no longer raises a "which did you mean?" question about two invented alternatives. A barred utterance also no longer *cancels* a live pending command or preempts a follow-up slot-fill — before, a phantom scored high enough to count as a complete new command and cleared whatever question was outstanding; now the pending survives it. The subtraction reaches **construction time** too: the Editor's sibling-tie warning is now withheld for a set whose discriminating word leads every member of it, so a grammar that used to be flagged at construction is silent — the entry below covers why. In the Editor a barred extraction round records no parse-diagnostic entry, so an author debugging a grammar sees a round that consumed words and produced neither a result nor a diagnostic line; for the same reason a barred utterance's `rejectReason` in the session log reads `no match` rather than a score rejection, and the batch test runner reports it as "no pattern matched" even though a pattern did match and was refused by position. One timing note if you set `prefixHoldSeconds`: the eager gate refuses a leading-missed candidate before it can arm the shortened hold, so such an utterance now waits the full `bufferWindow` before being reported unrecognised rather than the shorter prefix hold. Nothing fires either way; it is reported later. ([#124](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/124))

- **The construction-time sibling warning is withheld where the discriminating word leads *every* competing pattern, because what it said about such a grammar was not true.** The Editor's sibling-tie warning concludes its diagnosis with "so the wrong intent can fire", and then prescribes three remedies for that hazard — diverge by more than one element, mark the more destructive command `requiresConfirmation`, or turn on `disambiguateSiblingTies` — sometimes followed by a note about the disambiguation cap. Under the bar above that diagnosis is false whenever the word telling the two intents apart is **every** competing pattern's *first required element*: dropping it still leaves the patterns tied exactly — same score, same consumed span, same literal count — but whichever candidate wins the round missed its own first required element, so it is barred, that round yields nothing, and for that set no command fires and no disambiguation question opens. Each of the three remedies goes with it: there is nothing left to fire, so nothing left to redirect, to confirm, or to ask about. This is a **correction, not a further narrowing**: an author with an anchor-discriminated grammar was being sent to rewrite it against a hazard that did not exist, and the fix is to withhold the warning rather than reword it, since there is nothing left to report. **It takes every member of the set.** Where the discriminator leads one pattern and not another, the two still tie exactly, registration order can hand the round to a candidate the bar does not touch, and the warning fires as it always did — the withholding does not reach a mixed set. The new exclusion is **positional and consults no configuration**, unlike the existing one for pairs too short to clear `minScore`: that older exclusion is arithmetic and moves with the threshold you configured — see the entry under **Fixed** that made it read the configured one — while this one holds at every `minScore`, because what refuses the round is *which* element went missing rather than how much score survived. The warning's disambiguation cap note rides on it, so a withheld set spanning more than five discriminating values also loses the advisory that runtime disambiguation cannot put them all in one question — nothing shipped described that advisory, and it limited a question that is never asked for such a set. Three guarantees this changelog already claimed for the bar are now pinned by tests rather than asserted: `allowPartialMatch` opens no pending where the missing anchor is a **slot** rather than a literal, `requiresConfirmation` asks nothing, and `disambiguateSiblingTies` raises no question. Editor-only — the warning is `[Conditional("UNITY_EDITOR")]`, so a player build is unchanged — and nothing about parsing, scoring or firing moves with it. ([#124](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/124), [#128](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/128), [#130](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/130))

- **The documentation for both changes has landed with them, and three pieces of earlier advice are reversed rather than merely updated.** If you read the 1.5.0 docs, three things they told you are no longer true. `troubleshooting.md` told a user whose command scored `~0.50` to **lengthen the pattern**; that still works for a dropped word in the middle or at the end, but no length recovers a dropped *first* required element. `command-recognition.md` and `KNOWN_LIMITATIONS.md` both listed *"make the two commands differ earlier in the pattern"* under **what does not help**; it is now one of the more effective mitigations available, at any length, and it has picked up a second consequence those pages and `troubleshooting.md` now spell out — applied to *every* pattern of the set it also silences the construction-time warning for that pair, so a warning that disappears after you take the advice is the mitigation landing, not the hazard moving. And the `KNOWN_LIMITATIONS.md` entry for the sibling warning being silent below the default `minScore` had its repro replaced here, because the old form can no longer reproduce anything — the entry itself is then retired outright later in this release, under **Fixed**. `Documentation~/scoring.md` gains the rule's own section, and its glossary a **barred winner** entry; a new known-limitation entry records what the bar costs, with its measured incidence — of the 17 rows above that stop firing anything, 9 lose a genuinely spoken command and the other 8 were invented; and the session-log format description shipped inside every exported log is corrected, since a barred round writes no attempt at all. ([#124](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/124), [#129](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/129))

- **The leading-required-miss bar governs which candidate may *win a round*, not which may be offered as a disambiguation alternative — a distinction now documented and pinned by tests rather than left implicit.** The entry above says that with `disambiguateSiblingTies` set, a tie between two commands that **both** lost their leading word no longer raises a question; that remains exactly true. What it does not say, and what a reader could reasonably over-read it into, is the *mixed* case. Wherever that word is **not** every member's first required element — reachable because `{?ship}` and `{ship}` normalise to one element, so two siblings can disagree about which of their elements is first-required, and a member can therefore lose its own anchor while its sibling keeps one — the members still tie exactly, and registration order decides the round — a tie never displaces an incumbent, so where it hands the round to the member the bar does **not** touch, the barred member is offered alongside it as a choice and **fires if the speaker picks it**. Register the barred-prone member first instead and it wins, the bar refuses it, and the round yields nothing at all. Nothing about that is new in this release and no behaviour moved here: the bar has always been applied to the round's winner alone. It is recorded rather than closed because closing it would take the question away without taking the hazard away — where the discriminator is not the barred member's own anchor, both members of the round missed the same words — the shared verb and the discriminator — and the one that survives is admitted only because a matched leading **slot** sits in front of its verb. Refuse the barred rival and a two-member set falls below two choices, so no question is asked at all and that equally unheard survivor fires on its own; a larger set keeps its question and merely loses an option. Where the discriminator **is** the barred member's anchor the trade is worse again: each member then missed only its own discriminating word, so answering *supplies* the anchor that went missing, and refusing the rival would delete a question that was doing its job. The mitigations are unchanged and ordinary: `disambiguateSiblingTies` is off by default, don't author one member of a sibling pair with a leading optional slot where its sibling leads with the required form, and `requiresConfirmation` on the riskier intent does reach a chosen alternative, because the resolution re-enters pending on that alternative's own definition. ([#126](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/126))

### Fixed

- **A command that opens a slot-fill or confirmation prompt no longer *also* reports the same utterance as unrecognised.** Where `allowPartialMatch` routes a command missing a required argument into a pending, or `requiresConfirmation` holds a complete command back to ask before firing it, the recogniser raised `OnCommandPending` and then, in the same frame, raised `OnUnrecognisedSpeech` carrying the same text — telling the integrator the speech was not understood at the moment it was being asked to prompt the speaker about it. The two obvious integrations both misbehaved: a "didn't catch that" voice line played over the confirmation prompt, and any UI that clears itself on `OnUnrecognisedSpeech` tore down the prompt it had just been asked to show. The result loop already tracked exactly this distinction — a result that was *handled* rather than *rejected* must not also be reported unrecognised — and the disambiguation branch set that flag with a comment naming this precise harm; the partial-match and confirmation branches entered their pending without it. They now set it too, so all three pending reasons behave alike. Both flags are opt-in and neither is reached by the default grammar, which is why this survived. Nothing about parsing, scoring, or which commands fire moves: the only difference is whether `OnUnrecognisedSpeech` is raised for an utterance that opened a pending, and the utterances that genuinely match nothing still raise it exactly as before. ([#133](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/133))

- **The construction-time cancel-collision report is withheld wherever the ambiguity it warns about can never be put to the speaker.** That report tells a grammar author their discriminating value is also cancel vocabulary, so if the ambiguity were routed back to the speaker, answering with that word would cancel rather than choose — and its remedy is to rename a grammar literal. Two shapes never route it, and it is now silent on both. **By position**: where the word telling the intents apart is every member pattern's *first required element*, the leading-required-miss bar takes the round — dropping that word bars whichever member wins it, so nothing fires, no pending opens for that set, and no question is ever asked for the answer to be swallowed. **By score**: where losing that word drops the tie under `minScore` — a two-element pattern falls to `(2 − 1) / 2` = `0.5`, beneath the `0.6` default — both tying siblings are rejected by the gate, so again nothing fires and nothing is asked. On either shape the author was being sent to rename a literal to protect an answer that can never be given. The sibling-tie warning beside it already withheld on both; the collision report inherited neither, because it is narrowed per *pair* where the sibling filter is narrowed per *set*. Both are sound set-wide even so: if no question is asked for the set, no pair inside it can be asked about either. The score test is judged against the `minScore` you configured rather than a hardcoded default — the entry below is that change — so an author running a lowered threshold, where such a tie *is* live and *can* be routed, still gets the advisory. Editor-only, via `[Conditional("UNITY_EDITOR")]` on the call site, and nothing about parsing, scoring, or which commands fire moves. ([#132](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/132), [#140](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/140), [#124](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/124))

- **The construction-time sibling scan is judged against the `minScore` you configured, not against a hardcoded copy of the default.** `VoxrCommandParser` was built from the grammar alone and never saw the recogniser's threshold, so both of its Editor authoring messages — the sibling-tie warning and the cancel-collision report above — reasoned about reachability at `0.6` whatever you had actually set, and the error ran both ways. An author who had **lowered** `minScore` had genuinely live short ties go unreported, because at `0.6` the arithmetic said neither sibling could fire; that was a documented limitation, and the `KNOWN_LIMITATIONS.md` entry recording it is retired with this change rather than reworded. An author on the **default** got the opposite error, and it is the one this issue was reported for: the collision report consulted no score at all, so it advised renaming a literal on short pairs where no question could ever be asked. Both messages now read the threshold that will actually run — `VoxrCommandRecogniser` passes its configured `minScore` at both of its parser-construction sites, and `VoxrBatchTestRunner` passes the threshold it already accepted and previously dropped, so the warnings a batch run logs in the Editor are judged against the same gate the run itself applies. `VoxrCommandParser`'s constructor gained a final optional `float minScore` parameter, defaulting to `0.6`, to carry it. The type is **internal** — its `InternalsVisibleTo` grants name only this package's own test and editor assemblies — so this is not a public-API change and no integrator code is touched; appending the parameter last leaves every first-party call site compiling and behaving exactly as before, and those that supply no threshold still get the `0.6` fallback. What a package consumer *can* observe is the `VoxrBatchTestRunner` change above, since that type is public: its constructors now propagate the threshold they previously dropped, so an Editor batch run's authoring warnings follow the same gate the run itself applies. The value is read once, when the parser is built, so an Inspector edit reaches these messages at the next `RebuildParser` / `Configure` / `SetActiveSets` / `NotifySlotChanged` rather than on the next utterance; the runtime gate of the same name is untouched and still read fresh on every parse. **Editor-advisory only** — both messages are gated by `[Conditional("UNITY_EDITOR")]` on the call site, so a player build is unchanged and nothing about parsing, scoring, or which commands fire moves. ([#140](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/140))

## [1.5.0] - 2026-08-18

### Added

- **The parser now warns when one intent is registered by more than one command definition, instead of silently accepting it.** Registering two `VoxrCommandDefinition`s under the same `Intent` — in one `Configure` call or across two command sets made active together — is silently accepted today. Both definitions' patterns still compete in the parse and either can win an utterance; what only one of them is reachable for is resolution *back from the intent* — and the two places that do that resolution disagree about which: the command-set lookup is a dictionary keyed on intent, so the **last** registration wins there, while the follow-up re-score scans the command list and stops on the **first**. A `VoxrCommand` carries its intent and `MatchedPatternIndex` but not the command that produced it, so every consumer re-derives the definition from the intent string and can read the one that did not match — `MatchedPatternIndex` applied to a pattern of a different length, a different unfilled-slot set for a follow-up to chase, a different `allowPartialMatch`, and a different `requiresConfirmation`, i.e. whether a destructive command asks before firing decided by registration order rather than by the command that matched. The divergence itself is reported, not repaired — this was the root cause behind the non-positive follow-up score that [#113](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/113) floored. The warning names the intent, how many definitions carry it, and the first pattern of each of the two definitions the resolutions reach; the remedy is to move the patterns into a single definition, which is unambiguous everywhere. Registrations that no consumer could tell apart get a separate report and a separate remedy: nothing disagrees there, but only one copy is reachable from the intent and each extra ties the original exactly in the parse — the usual causes being a set named twice in one `SetActiveSets` call and one command asset placed in two sets that are active together, since `Activate` concatenates the active sets without de-duplicating. Editor-only, like the two authoring scans beside it, and appended after them so existing ordered log expectations are unaffected. Intents are compared ordinally, matching both lookups. Nothing about parsing, scoring, or firing changes. ([#120](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/120))

- **The Editor now tells you when a command won on registration order alone — including when the rival was not a sibling.** The debug window's last-match breakdown and the batch test window's per-result diagnostics gain a tie line naming the rival that scored exactly as well as the winner, and saying which kind of tie it was: a *sibling* (one dropped word apart — the shape `disambiguateSiblingTies` exists to answer) or *not a sibling*, which means duplicate or overlapping patterns in the grammar. The distinction is the point. Everything else in this unreleased block treats a tie as sibling-only, and rightly so — the discriminating values are the choice vocabulary, so a tie with no such values is a tie there is no question to ask — but that also meant a **non**-sibling tie was recorded nowhere and read as "nothing tied". Register two intents on the same pattern and the second can never fire; nothing warned, because the construction-time sibling warning fires only on patterns that differ at exactly one position and these differ at none, and the panel showed a clean `1.00` PASS. The same silence covered two patterns tying by accident and a command whose second phrasing is dead. Nothing about parsing, firing, or the runtime choice list changes — the tie line is a report, the winner is still correct by every rule the parser has, and a player build is untouched in either configuration of the flag. ([#95](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/95))

- **The recogniser can now ask which command you meant instead of guessing.** Where two commands differ by exactly one word and the recogniser dropped that word — `set {ship} mode on` against `set {ship} level on`, heard as "set alpha on" — the surviving evidence fits both *exactly* equally, so selection exhausts every key it has and falls through to registration order. Earlier work in this same unreleased block made that coin flip visible to the grammar author (a construction-time warning) and stopped the eager gate committing it early (the gate now defers to the flush). Neither changed what the flush does: it still fired the first-registered sibling. **This is the piece that makes that deferral worth paying for.** Set `disambiguateSiblingTies` on `VoxrCommandRecogniser` and an ambiguous flush stops, raises `OnCommandPending` carrying the candidate that *would* have fired, and exposes the competing commands through the new `PendingAmbiguity` property — a `VoxrPendingAmbiguity?` holding the choices, the single word that tells each apart, and whether the list is complete. The speaker says one word (`mode`, `level`) and the right intent fires with its slots intact, through `OnCommandConfirmed` then `OnCommandRecognised` — or, where the chosen command sets `requiresConfirmation`, asks *that* next, so the exchange runs "which?" then "are you sure?", which is the order taking this feature's own two remedies together produces. The answer needs no grammar work: discriminating values are pattern literals, so the decoder already has them — pinned by comparing the generated grammar JSON byte-for-byte across the flag. **Off by default, and not out of timidity**: with the flag on an ambiguous utterance fires *nothing* until it is answered, so an integrator with no `OnCommandPending` subscriber would lose the command entirely — worse than the coin flip it replaced. `PendingAmbiguity.HasValue` is how a handler tells a "which did you mean?" from an "are you sure?", which matters because `OnCommandPending` carries no reason and anyone already subscribed for `requiresConfirmation` would otherwise prompt yes/no at a speaker who needs to say a word. **The choice set is n-ary**, not a pair: `set auto pilot on` / `off` / `standby` offers three, and each one-word answer fires its own intent; the runtime offers the winner plus up to four alternatives, and `IsTruncated` reports whenever some answer the speaker could have given is not on the list, so a prompt can add "…or say the whole command again". Answering follows the existing follow-up rules — cancel keeps precedence over a choice (the author is warned at construction when a discriminating value is also cancel vocabulary), a full re-utterance preempts the question, and "yes" is inert: not an answer to "which?", but not an abandonment either, so the question stays open. On timeout nothing fires **even under `pendingTimeoutBehavior = FireAsIs`**, because there the *intent* is unknown rather than the arguments, and firing the first-registered after a pause is the same coin flip merely later. Two interactions are worth knowing: under push-to-talk with `cancelPendingOnRelease`, release flushes and then cancels, so the question is destroyed before it can be answered; and a rival whose pattern carries more than six optional elements can be proved to tie but not *named*, so it is never offered as a choice (reported through `IsTruncated` when a question is asked anyway). With the flag off, parse and fire behaviour is byte-identical — measured across the 699-utterance corpus, every intent, slot and score unchanged, with allocation identical to the byte. Three Editor-only *messages* do change regardless of the flag, which is the next entry. ([#74](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/74))

- **The sibling warning's element number now indexes the pattern it quotes**, and the cancel-collision report is judged against the vocabulary that will actually run. The warning prints the patterns as you authored them but numbered the differing element by its position in the *collapsed frame* the parser matched on, so a pattern whose optional elements were omitted for comparison was quoted whole and numbered short — `?please switch to weapons` reported "element 3", which is `to`. Members that agree on the position keep the existing wording; where they disagree, each quoted pattern now carries its own number. The same defect sat one message over in the cancel-collision report and is fixed with it. That report also stops guessing about your configuration: it now tests **your** `cancelVocabulary` when you set one, so a collision you resolved by overriding the vocabulary is no longer reported and one you *introduced* with an override is, and the message names the right source and offers the remedy that still applies. It is also narrowed to values that could really be given as an answer — a value whose only same-set partners share its intent is never routed to the speaker, so warning about it was advice about a question that never gets asked. ([#91](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/91))

- `Documentation~/scoring.md` — a reference for the matching and scoring model, which until now existed only as `internal const`s in `VoxrCommandParser` and rules spread through its selection loop. It covers the per-element score table (matched required literal/slot `+1.0`, matched optional literal `+0.5`, missed required literal `0`, missed required slot `−1.0`) and the dynamic denominator, with the consequence that a missed literal is charged once — the credit is withheld while the element keeps its place in the denominator — so the same dropped function word scores `2 / 3` = `0.67` on a three-element pattern and clears the default gate, but `1 / 2` = `0.50` on a two-element one and does not; coverage and its rules (charged on both sides of the match and applied *during* selection, so it decides which pattern wins; the orphan test that stops counting at the first token another pattern could begin on, and the one exception to it; `[unk]` never charged and transparent rather than a run terminator; counting restarts per extracted command; proportional); the full selection order — earliest start beats everything, then score, then consumed span, then literal count, then registration order — and that `TryEagerCommit` mirrors it, so an eager verdict never names a command the flush would not fire; sequential extraction and what it means for patterns that prefix others; the two gates, including that confidence is the *minimum* per-word value over the matched span rather than an average (one weak word vetoes an otherwise-perfect command — a `1.00` match rejected at `0.39`), the ~0.5 ceiling on "two", and the `-1` "no data" sentinel that bypasses the check entirely; the three eager-flush verdicts with the six conditions any verdict above `None` requires, plus the terminality test that separates `Commit` from `HoldExtendable`; and five worked examples traced from candidate scoring through selection to the gates, each ending in the session-log entry it produces. This makes the auto-exported session log self-interpreting: its `score`, `minScore`, `aggregateConfidence`, and `rejectReason` fields are the right diagnostic data but were unreadable without the formula, so the page closes with a field-to-rule map and a symptom table for the rejections that account for most of them. Every number in it was measured by driving the real parser sources, not derived by hand. Cross-linked from the docs index, the command-recognition guide, `api/command-recogniser.md`, the troubleshooting guide (which gains two new symptom entries — a command that fires with a slot missing, and the `~0.50` short-pattern rejection), and the session log's own `readme` field. The same pass corrects what an `attempts` entry actually is, in both that `readme` string and the editor-testing guide: it is one *extraction round* reporting the pattern that won selection, not "every command definition evaluated against the utterance" — losing candidates are never recorded, so a pattern's absence means it lost selection rather than that it was never tried, which is the opposite of what a reader would conclude from the old wording. Writing it also turned up three things the existing docs had wrong, all corrected here. **`OnUnrecognisedSpeech` was documented backwards**: `command-recognition.md` and `api/command-recogniser.md` both said it fires when matches are rejected by `minScore`, `minConfidence`, or debounce, but the suppression flag is set *only* on the confidence and debounce paths — so a score-rejected utterance (the guide's own headline failure) does raise the event, a partial-match or confirmation diversion raises it alongside `OnCommandPending` (a *disambiguation* diversion, added later in this same block, deliberately does not), and confidence/debounce rejections are the two that stay silent. **A `-1` confidence was attributed to an all-`[unk]` matched span**, which cannot occur — selection never starts a match on `[unk]` — where the real second cause is a matched span carrying no word data of its own, which can happen with the `words` array populated. And **the aggregate confidence is resolved per distinct word text, first occurrence winning**, so a word repeated in one utterance is scored at its first occurrence everywhere it appears, even when that occurrence lies outside the matched span — measured, not inferred: "orient heading two **two** zero" with the repeat at 0.39 reports 0.85. `KNOWN_LIMITATIONS.md`'s `-1.00` entry carried both of the last two errors and is corrected with them — it described the parser as unable to "compute a meaningful average" of a value it has only ever taken the minimum of, and reproduced the sentinel from a leading `[unk]` run that cannot in fact produce it. Documentation only — the sole code edit is that `readme` string, and the log's `schemaVersion` is unchanged because its shape is not. ([#47](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/47))

- The parser now warns at construction when two commands are separated by a single word, so an author learns about a coin flip before shipping it. Two patterns identical but for one required literal — `switch to weapons` and `switch to navigation` — tie on *every* selection key once the recogniser drops that word: same start, same score, same consumed span, same literal count. Selection exhausts its keys and falls through to its last, the order the patterns were registered in, and the wrong intent fires with nothing in the log flagging it as ambiguous. The word that would have decided is precisely the word that went missing, so no scorer can recover the intent — the evidence is not weak but absent, which is why this ships as an authoring warning rather than a scoring change. Nothing about parsing changes in *that* pass: same commands, same scores, same selection, same eager timing. (The eager timing does change later in this same unreleased block — see the sibling-tie entry under **Changed**, which stops the gate committing early on this shape.) **The differing word may sit anywhere in the pattern, and the middle is worse than the end.** A trailing discriminator is at least refused by the eager gate, which will not commit a pattern whose trailing required element never matched; a *medial* one clears that guard, because the elements after it still match and the tail check resets — `set {ship} mode on` heard as "set alpha on" scores `3 / 4` = `0.75` and spans the buffer, so at this point in the work it committed **early** with the wrong sibling. That had been reasoned from the source and never observed; landing a test for it is what made the sibling-tie refusal below possible, and that refusal is what stops the early commit. The same test also pins the flush half, where reversing two declarations flips which intent fires on an identical utterance — which is still true, and is what issue #74 remains open for. **The warning reports only what it can see going wrong**, and the two narrowings are measured rather than assumed. Patterns of the *same* intent are excluded: the same command dispatches whichever wins, so the "tie" is between two phrasings the author deliberately made equivalent — six of the shipped demo grammar's eleven sibling sets are that shape, every one of them ordinary synonym authoring (`set` / `hold` / `keep` / `maintain distance`). Ties that cannot clear the default `minScore` are excluded too: losing one required element from a pattern worth `D` leaves `(D − 1) / D`, so a two-element pattern drops to `0.5`, under the gate, and *both* siblings are rejected — nothing fires, rather than the wrong thing, which the suite already pinned twice and which makes "the wrong intent can fire" the wrong thing to tell an author. The test weighs elements rather than counting them, since a matched slot credits `1.0` whether or not it is optional and only an optional literal credits `0.5`: `switch ?to weapons` lands on exactly `0.60` and warns, `cease fire` sits at `0.50` and does not. Together those take the shipped sample grammar from eleven detected shapes to **one** emitted warning — the issue #74 pair itself. The message names the intents once each, every implicated pattern as authored, the 1-based element they differ at, and the competing values, and offers only remedies that exist today (make the two commands differ in more than one element — the only fix that removes the tie rather than moving it; or mark the more destructive one `requiresConfirmation`). A companion warning fires when a discriminating value is also in the default cancel vocabulary — `cancel`, `abort`, `negative` — because follow-up handling checks cancel first, so if that ambiguity is ever routed to the speaker to resolve, answering with that word would cancel rather than choose. **Editor-only**, via `[Conditional]` on the call site, so a player build pays neither the message nor the scan that produces it. The one cost is stated in `KNOWN_LIMITATIONS.md`: the parser is constructed with the grammar alone and never sees the recogniser's configured threshold, so it judges reachability against the default — run below `minScore` `0.6` and short sibling pairs become live without the warning noticing. The reverse error would be worse, putting a knowingly false claim in front of every author who left the knob alone. ([#74](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/74))

- The parser now warns at construction when a command's pattern set carries a common shape that silently discards a slot value the speaker did say: a bare pattern plus a sibling that extends it with a required literal followed by a slot (`decelerate` and `decelerate by {burn_level}`). Drop that literal — short unstressed function words are the tokens VOSK drops most, and speakers elide them — and the slot-filled pattern is charged for the missing required word (the withheld credit, 1.0) while the bare pattern still matches perfectly (1.0), so the bare pattern wins, sequential extraction finds nothing to do with the recognised "hard burn", and the command runs at its default level with nothing reporting the loss. Observed in-headset. No threshold or penalty tuning reaches this — a score normalised to 1.0 is the ceiling, so nothing can outrank an exactly-matching bare pattern — which is why this ships as an Editor-only authoring-time warning naming the literal and the slot at risk, plus the fix: mark the literal optional (`?by`). An omitted optional leaves both sides of the score ratio, so the slot-filled pattern then also scores 1.0 with or without the word and wins as the candidate covering more of the utterance, while a bare "decelerate" still matches the bare pattern. The warning covers optional trailing slots too (`orient heading {heading} mark {?elevation}` strands the elevation the same way), and the shipped command-recognition sample and demo grammar have been switched to `?mark` accordingly. **The check follows what selection actually compares**, so it catches the hazard in every form it takes: across two different intents as well as within one command's pattern set (selection runs over every pattern of every command), behind a run of two or more required literals rather than exactly one, and after expanding a bare pattern's own optional elements — `fire {?quantity} {weapon}` is not literally a prefix of `fire {weapon} at {target}` but is once the optional is omitted, which is the form the parser matches when no quantity is spoken. Patterns carrying more than six optional elements are compared unexpanded, since the scan runs on every parser rebuild an Editor session makes and expansion is exponential; that costs recall on those patterns only. **The remedy also has a price**, now documented alongside it: an optional literal scores 0.5 rather than 1.0 on both sides of the ratio, so *imperfect* matches score strictly lower than before and may fall under `minScore`, and it stops anchoring the element behind it, letting a following slot claim adjacent tokens the literal never introduced. Parser behaviour is otherwise unchanged — the parser only logs — though the `?mark` edit does change which pattern the sample's `set_heading` selects on some utterances. **The warning is Editor-only**, and deliberately so: coverage (below) closed the common case, so the shape it flags now behaves correctly in most grammars, and the trigger stays at full breadth because a narrowing could only consult the start-set half of the orphan test and would go silent on every position the wider admissibility test (#82) accepts — and because setting `coverageWeight` to `0` restores the hazard wholesale, where it is not residual at all. That is guidance worth giving where grammars are authored, not a warning worth logging in every player build and re-emitting on every `SetActiveSets` rebuild, where its breadth would earn it a blanket suppression that took the residual case with it. ### Changed

- **Behaviour change — the eager-flush gate no longer commits early when the buffer fits two different intents equally.** Where two patterns of *different* intents tie on every selection key and differ at exactly one required word, the winner is decided by registration order alone; firing that immediately commits a coin flip before the speaker has finished. The gate now declines and lets the buffer run its full window. **The same command still fires** — at the end of `bufferWindow` rather than at once — so no integration loses a command; only its timing moves, and only on this shape. It is not behind a flag, because it is safe either way: the flush picks the first-registered pattern exactly as it always has. This closes the *medial* case the gate's existing tail rule structurally cannot see — `set {ship} mode on` against `set {ship} level on`, heard as "set alpha on", which scores `3 / 4` = `0.75` and spans the buffer. Deferring does **not** let the missing word arrive: speech only ever appends, and the position that word would have occupied is already behind the match. What it buys is that the guess is made once, on a final transcript, which is where a future release can ask the speaker which command they meant. Measured against the 699-utterance corpus: every fired intent, slot and score identical, and every eager verdict identical — the corpus's one reachable sibling tie is a *trailing* discriminator the tail rule already refused, so it serves as a control rather than as evidence. Two narrowings are worth knowing. A tie between two phrasings of the *same* intent still commits, since the same command dispatches either way. And a pattern carrying more than six optional elements is compared only in its required-element reading, so a sibling relation visible solely in some middle reading of it is not seen — recorded in `KNOWN_LIMITATIONS.md`. Also fixed in the same pass: sibling sets now name **every** pattern carrying a hazard instead of dropping one that repeats a discriminating value, which previously could leave the survivors sharing an intent and suppress the warning entirely. ([#74](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/74), [#90](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/90))

- A command is now scored on how much of the utterance it explains, not on how neatly it matched the part it chose. Coverage charges a candidate for the in-grammar tokens it leaves unexplained on **both** sides of its match, and — the change that does the work — computes that charge **before** candidates are compared rather than applying it to the winner afterwards. The leading skipped-word term from #31 sat after selection precisely so it could not reorder anything; symptom 2 of #65 cannot be fixed under that constraint, because a bare pattern that matches perfectly scores `1.0` and nothing normalised to `1.0` can be beaten at any penalty setting. So the barrier goes: `score = rawScore / (denominator + (skippedBefore + orphanedAfter) × coverageWeight)`. A grammar registering both `decelerate` and `decelerate by {burn_level}`, hearing "decelerate hard burn" with the "by" dropped, used to fire the **bare** command and discard the burn level with nothing in the log to signal it; the bare form is now charged `1 / (1 + 2)` = `0.333` against the slot-filled `2 / 3` = `0.667`, so the command fires **with** its argument. A trailing token counts as unexplained only if no active pattern could begin a match at it, and counting stops at the first token that could — which is what keeps multi-command utterances intact ("cease fire launch missiles target hotel one" still scores `2/2`, not `2/7`), and what makes the follow-up confirm/cancel vocabulary safe, since the parser is now told the same word list the decoder was given. `[unk]` is never charged and is transparent rather than a run terminator, so one noise token cannot shield every real orphan behind it. One exception, at the run's first position only: a token the candidate's own next required element just failed to match is always charged — without it a pattern that **missed** its final element could stop short of a token that terminated its orphan run while the pattern that **matched** it paid for everything after, and the wrong command won (`switch to weapons target hotel` selected `mode_navigation`). **This is a behaviour change with no opt-in, and it is default-on.** Measured over 699 utterances against the previous release: nothing newly fires, no command loses a slot, 11 change intent and 17 stop clearing `minScore` — commands that used to fire and no longer do, listed with their causes in `KNOWN_LIMITATIONS.md`. (Those 11 are recovered later in this same unreleased block, by the #82 entry under **Fixed**, which also removes the `KNOWN_LIMITATIONS.md` entry that recorded them; the net for the release is stated there.) Set `coverageWeight` to `0` to restore the previous scoring entirely, at the price of restoring the discarded-argument bug with it. ([#65](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/65), [#42](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/42))

- **Breaking (Inspector-safe):** `skippedWordPenalty` is renamed to `coverageWeight` on `VoxrCommandRecogniser` and on both `VoxrBatchTestRunner` constructors, because one weight now governs the leading *and* trailing charge and the old name described only half of it. Values already set in the Inspector survive the upgrade via `[FormerlySerializedAs]`. Code calling either `VoxrBatchTestRunner` constructor with a **named** argument (`skippedWordPenalty: 0.5f`) must update; positional callers are unaffected. Note that `[FormerlySerializedAs]` covers a field's own serialized data — a prefab-*instance* override of the old field is stored as a literal property path and may not migrate, so re-check any prefab that overrode it.

- **Behaviour change — a dropped function word no longer silences a short command.** A missed *required literal* was charged twice: it withheld its credit **and** subtracted a `-0.5` penalty while still occupying the score denominator, so one dropped word cost `1.5/N` of a ceiling fixed at `1.0`. Because that cost is a fraction of pattern length, it fell hardest on the patterns least able to absorb it — `time to target` heard as "time target" scored `0.50` against the `0.60` gate and did not fire at all, while a seven-element pattern shrugged off the identical drop at `0.79`. Pattern length, not pattern quality, decided whether a command survived. A miss now costs `1/N`: the same three-element pattern scores `2/3` = **0.67** and fires, and the seven-element one `6/7` = **0.86**. Reduced, not abolished — the cost stays proportional to length, so a **two**-element pattern missing half its evidence still scores `1/2` and is still refused (`cease fire` heard as "fire" is genuinely ambiguous with a registered `fire`). Missed required **slots** are untouched at `-1.0`: an absent argument is not a dropped function word. **Existing grammars re-score on upgrade; there is no opt-in and no compatibility mode.** Measured over single-word ablations of the committed acoustic corpus, 10 of 61 degraded transcripts go from silently rejected to recognised, 9 of them recovering the intent the undamaged transcript produces. ([#65](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/65))

- **Behaviour change — selection now refuses candidates with more missing required elements than matched ones.** Removing the miss penalty above also removed a filter it had been applying by accident, and the effect was not confined to harmless low-scoring tail results: because selection ranks *earliest start* above score, a sparse fragment could win an extraction round outright, consume the tokens ahead of a real command, and thereby change that command's score — in one measured case firing a command at `1.00` that the skipped-word penalty had correctly held to `0.50`. Admission is now stated as a rule: a candidate whose missed **required** elements outnumber its matched ones is not a candidate. Optional elements count toward neither side. This is a count, not a threshold — nothing to configure, unrelated to `minScore`. The visible effect is that a very sparse partial match now yields *no* result rather than a low-scoring one; see `Documentation~/scoring.md` §3. ([#65](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/65))

- The generated VOSK grammar is no longer a flat list of single words: contiguous literal runs from each pattern and multi-word slot surface forms are now emitted as **phrase entries** as well. A word-list grammar discards every sequence constraint the patterns declare — the decoder is free to assemble any in-grammar words in any order, so acoustically-near in-grammar neighbours substitute for each other with nothing structural resisting. VOSK charges one language-model transition per grammar entry, so a *k*-word phrase entry costs one transition where the same words cost *k*; the declared order becomes the cheaper path through the search, which is what re-imposes it. A slot or an optional literal **ends** a run (neither is guaranteed to be spoken, so the words either side of it are not reliably contiguous): `close distance {range} target {target}` yields `close distance` and `target`, never `close distance safe range`, and `launch ?a {?quantity} …` never welds `launch a`. Individual words are **deliberately kept** alongside every phrase, so the grammar is a strict superset of the previous one — nothing that decoded before stops decoding, an utterance the VAD splits mid-phrase still resolves as fragments, and the sequence constraint is a bias rather than a hard rule. Measured against the real decoder rather than assumed: replaying the committed 16-fixture corpus through the Tier C desktop harness (libvosk 0.3.45, same model, same AGC gain) leaves 15 transcripts byte-identical and **corrects one** — `switch to navigation`, which decoded as `switch two navigation` and matched no command, now decodes and fires `mode_navigation`. That fixture had been pinned as a negative homophone baseline precisely so an improvement would surface for conscious re-baselining; it is re-baselined here as a positive, in both the corpus manifest and the harness transcript baseline. The demo grammar grows 98 → 133 entries (35 phrases), a bounded cost since entries are enumerable from the assets. A phrases-only variant — dropping the 38 single words that occur only inside phrases — was measured too and produced *identical* transcripts on the corpus, so the single words are kept for the fragment robustness they buy at no observed cost. Parser, scoring, selection, and every consumer-facing API are untouched; only the hypothesis space the decoder searches gets tighter. Two caveats: confirm/cancel follow-up vocabulary is flattened to words by its caller before reaching the emitter, so multi-word follow-ups (`never mind`, `go ahead`) are not phrase-chunked; and the corpus is TTS speech, so the gain against the human-speech confusion pairs this targets (close/coast, full/four, clicks/six) still wants an in-headset A/B. ([#45](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/45))

- A grammar the eager-flush eligibility analysis cannot process no longer costs the whole command set the feature outright. The precompute refuses to analyse a pattern carrying more than 12 optional elements — expansion enumerates 2^optionals concrete forms, and a partially analysed set could let a real prefix commit and fire the wrong command — and that refusal is necessarily set-wide, so every command in such a set reported no eager verdict at all and paid the entire `bufferWindow`. It now degrades to the *held* verdict instead: nothing commits early, which is precisely what the missing analysis would have had to vet, but a buffer that already parses as one complete, confident, whole-buffer command is held like any other complete-but-extendable match, so it waits `prefixHoldSeconds` where that is set — 0.6s rather than 2.0s of dead air on Quest 3 — instead of the full window. Grammars leaving `prefixHoldSeconds` at `0` keep exactly the previous timing, and the gates above the degrade are untouched: partial speech mid-split-command and speech matching nothing still report no verdict and keep the full window. The condition is also surfaced where it can be acted on. It is knowable from the command assets alone, so the parser now warns **at construction**, naming the offending pattern, its intent and its optional count, alongside the other authoring-time validation warnings — where before the only signal was a lazy runtime warning that named just the intent, fired mid-session on the first eager probe, and never fired at all for an author who had not yet enabled `eagerFlushOnCompleteMatch`. That runtime warning is gone, so the condition is reported whether or not eager flush is ever enabled, and every over-limit pattern is named rather than only the first one the precompute happened to reach. ([#44](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/44))

### Fixed

- **Switching `ListeningMode` after the assigned recogniser has been destroyed is now a no-op instead of a silent call into the destroyed component.** The setter was the only place in `VoxrPushToTalkController` reaching the recogniser through `?.`; every other site — `PressTalk`, `ReleaseTalk`, `Start`, `OnEnable`, `OnDisable`, `OnApplicationPause`, `Update` — used an explicit `!= null`. That distinction is the bug: `VoxrSpeechRecogniser` is a `UnityEngine.Object`, whose overloaded `==`/`!=` report a destroyed component as null while its managed wrapper is still alive, and C#'s `?.` performs a plain reference check that never calls the overload. A destroyed recogniser therefore read as non-null and the call was dispatched into it. That failure was silent rather than loud, which is why it survived: `StartRecognition()` hands off to a discarded `async Task`, so the `MissingReferenceException` that `StartCoroutine` raises on the Android permission path is captured onto a Task nobody observes, and the stop direction touches no Unity-side member at all. The visible symptom was simply a controller driving a component Unity considers dead — recognition that never started, and a recogniser that was never really stopped. Both transitions now use the same explicit check the rest of the file does. Riding along is the pairing question the `?.` had left unanswered: `OnTalkStarted`/`OnTalkEnded` were invoked unconditionally, so a controller with no live recogniser announced a start that never happened and, worse, an end that no start had paired with. Each event now fires inside the null guard, beside the `StartRecognition()`/`StopRecognition()` that earns it — the rule `ReleaseTalk` and the authored-`Continuous` enable already keep. The mode still changes either way, and a controller whose recogniser is assigned and alive — every ordinary scene — behaves exactly as before. ([#115](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/115))

- **A follow-up slot-fill can no longer deliver a command whose score is zero or negative.** Both flush paths floor candidates at `Score <= 0` before anything reaches a subscriber, and [Matching and Scoring](Documentation~/scoring.md) states the rule without qualification — a candidate scoring zero or less is discarded and never competes. The re-score that runs when follow-up speech fills a pending command's slots had no such floor. It is reachable when two definitions are registered under one intent, because the two halves of that path then resolve the intent differently: the completeness check reads the command-set lookup, which keeps the *last* registration, while the re-score scans the parser's command array and takes the *first*. The short definition calls the merged command complete; the long one charges it for required slots the matched pattern never had, and a `-0.11` command fired through `OnCommandConfirmed`. A fill that **completes** a command is now refused when it re-scores at or below zero: the pending is left standing, and the session log carries a `follow-up re-score ... <= 0` reason. A fill that only **partially** completes one still progresses exactly as before — it is re-armed with the slot it filled and a fresh `pendingTimeout` window, because refusing there would strand the exchange rather than floor it, and the pending retains its previous admissible score rather than storing the non-positive one, since `Complete`, the confirm-word arm and `FireAsIs` all deliver a pending's command without re-testing it. Grammars with one definition per intent are unaffected in every respect: there the two halves read the same pattern, and the admission rule makes a post-fill re-score positive by arithmetic. ([#113](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/113))

Warnings only — nothing is rejected, and a grammar whose alias keys were already lowercase and punctuation-free logs exactly what it logged before. - **An all-literal grammar can now be authored in the Inspector.** `VoxrCommandRecogniser.Awake()` treated an empty **Slot Assets** list as "nothing wired" and returned before converting anything, so a component whose commands declare no slots (`cease fire`, `weapons mode`) skipped its command sets too — neither `Configure()` nor `SetActiveSets()` ran, and nothing was logged. The symptom was a recogniser that heard speech and recognised no command at all, with the docs prescribing a `Configure()` call from code as the only way to declare such a grammar. **Slot Assets** is now simply optional: absent or empty, it converts with zero slots, and only **Command Set Assets** has to be populated, since that is the list carrying the commands. That leaves exactly one asset-list skip, and it no longer returns in silence — an empty **Command Set Assets** warns and names itself, though only when **Slot Assets** carries assets, so the ordinary code-driven component with nothing wired in the Inspector stays quiet and `Configure()` from `Start()` is not second-guessed. One skip stays deliberately silent and is now documented as such: a `Configure()` call landing before this component's `Awake()` claims the component, and `Awake()` then ignores both lists however they are filled in. Nothing about conversion, parsing, or scoring changes for a grammar that does declare slots. `Documentation~/inspector-authoring.md` documented the both-lists-required behaviour and has been corrected; `api/command-recogniser.md`'s Inspector-field table, which said nothing either way, now states the rule. - **A scene authored with `Listening Mode = Continuous` now fires `OnTalkStarted` when it starts listening.** Recognition began on enable but the event did not: it was invoked only from `PressTalk()` and from a runtime *change* to `Continuous`, so the one path with neither — a scene already set to `Continuous` when it loaded — opened the mic in silence and left a recording indicator wired to the event dark for the whole session. The intent to recognise is now recorded in `OnEnable`, beside the `StartRecognition()` it authorises, rather than in `Awake` where nothing announced it. Lifecycle handling is otherwise untouched: a disable/enable cycle and the Quest home overlay still resume silently, and only that first enable announces. That now stays silent, and the announcement waits for the tick that actually starts recognition. If you worked around this by driving the indicator off `VoxrSpeechRecogniser.IsRecognising`, that still works — the event is now an alternative rather than a trap. - A second command spoken in the same breath no longer costs the first one its score when the decoder drops the second's leading word. Coverage stops charging trailing tokens at the first one another match could begin at, but that test asked only what patterns *start with*, while selection tries every pattern at every token — so a pattern whose leading elements VOSK dropped begins wherever its surviving elements do, and the two disagreed about exactly the tokens that matter. "cease fire" + "approach target hotel one" heard as **"cease fire target hotel one"** charged `cease_fire` for all three trailing tokens, because "target" begins no pattern, even though `approach target {target}` does match there and the next extraction round did go on to fire it: `cease_fire` fell `1.0` → `0.4` and stopped firing, so the command spoken *cleanly* was the one lost while the damaged one fired. The terminator now asks the matcher — a token is a start if some active pattern, matched from it, ends up having matched **strictly more** of its required elements than it missed. That margin is what keeps this from being the crude widening the design refused, and it is deliberately one notch stronger than the admission rule selection applies: admission decides whether something is a candidate at all, while terminating another command's orphan run moves score off a command that *is* firing. One notch weaker and the slot value a bare pattern strands would terminate that bare pattern's own orphan run — `decelerate ?by {burn_level}` reaches `{burn_level}` from "hard" having missed one required element and matched one — restoring the [#42](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/42) discarded-argument bug on the very grammar the docs prescribe as its remedy. Like the admission rule this is a count, not a threshold: nothing to configure, independent of `minScore` and of `coverageWeight`. The probe runs once per utterance rather than once per candidate, and only where the cheap first-element test already said no. **Measured over the same 699 utterances the coverage design was ruled on, against the current `main`: 12 utterances recover a command that had stopped firing — 11 intent changes and 1 count change, the exact residue [#65](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/65) deferred — and every other behavioural column is zero: nothing newly fires, nothing goes silent, no command gains or loses a slot. 4 further utterances change score without changing what fires.** Of the ~50 documented scores the local doc harness pins and replays through the real parser, exactly one moves: `scoring.md`'s worked example D, which was this bug written up as a limitation and is now the worked example of the rule working. `KNOWN_LIMITATIONS.md` loses that entry outright. Eager-flush verdicts are unmoved on all 699. The exhaustive start-index sweep behind the neighbouring "demoted winner blocks a later match" entry was re-run: 29 blocked / 28 recovered / 1 silent becomes 28 / 27 / 1, so that entry keeps both its root cause and its single measured case. Cost, measured on the same corpus: **~12.3 → ~16.1 µs per `Parse`**, at **no added allocation** — 492.8 bytes per utterance before and after, because the probe asks the number matcher to skip building the joined slot value it would only discard, which is the allocation the cheap predicate avoids by construction. The time figure is for the flush path; the same sweep also runs once per partial result when `eagerFlushOnCompleteMatch` is enabled, and is skipped entirely at `coverageWeight` `0`, where no orphan count can reach a score. Selection keys, the admission rule itself, `[unk]` handling, the Amendment A3 rule, and `coverageWeight` are all untouched; A3's charge shifts only where the new terminator ends a run earlier. ([#82](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/82))

- The **Batch Test Runner** window now forwards `coverageWeight` to the runner it builds, so its results can be made to track the recogniser they exist to predict. The window mirrors `minScore` and `minConfidence` as serialized fields and passes both to `VoxrBatchTestRunner`, but there was no third mirror — so the window's parser ran at the default `1.0` however the project's `VoxrCommandRecogniser` was tuned, while `Documentation~/editor-testing.md` told authors to pass their tuned value "so batch results track runtime behaviour", an instruction the first-party window did not itself follow. What that costs is not confined to a moved score: `Run` accepts the first candidate clearing the thresholds and stops, so a weight the window failed to apply can hold the leading candidate under `minScore` and let the intent behind it through, and the window then reports a command the runtime does not fire. The plain rejection case is easier to see: on a grammar registering only `cease fire`, the utterance "cease fire please now" strands two trailing tokens no active pattern could begin a match at, scoring `2 / (2 + 2)` = `0.50` at the default weight against `2 / 2` = `1.00` at `0` — so a project tuned to `0` watched the window refuse a command the runtime fires, with no field to correct it. The gap **predates** [#65](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/65) and was verified against the base revision when it was split out of the #78 review: the pre-#65 charge applied after selection and could not reorder candidates, but the stop-at-the-first-accepted rule meant a charge that pushed round 1 under `minScore` already promoted round 2's different intent. Coverage widened it rather than opening it. The new field defaults to `VoxrCommandParser.DefaultCoverageWeight` rather than to a copy of it, and is drawn beside the two existing thresholds as **Coverage Weight**; a window nobody touches behaves exactly as it did. One unrelated correction caught while reviewing this change: `KNOWN_LIMITATIONS.md` quoted `editor-testing.md` as advising that batch results "predict runtime behaviour", a phrase that page has never used — it says "track" — and the misquote predates this change. ([#80](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/80))

- Follow-up slot-fill no longer fires a command that is *still* missing a required argument. [#73](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/73) refused that shape on the flush path and routed such commands to the pending/slot-fill path instead — which made this the designated destination for exactly the commands #73 will not fire, and it did not re-check them on the way out. `TryFollowUpSlotFill` walks the pending's unfilled slots in pattern order, stops at the first it cannot fill, and returns a command as soon as **one** new slot is filled; with two or more unfilled required slots an utterance answering only the first therefore produced a command `IsIncomplete` would reject, which was then completed and fired. The re-score does not stand in for the test — `ScoreFollowUp` re-scores against the matched pattern, so a partly filled command can score alongside a complete one, which is the "score is not a completeness test" argument #73 was decided on. The completeness condition now applies at this exit too. A fill that leaves a required slot outstanding is treated as **progress rather than a command**: the pending stays live carrying what was just filled, `OnCommandPending` fires again with the updated command so a prompt can name what is still missing, and the command fires only once nothing required is left. The fill is kept rather than discarded, so answering one slot per utterance works, and an unanswered remainder now reaches the timeout instead of firing, where the default `Cancel` discards it. **`pendingTimeout` is now restarted by each fill** rather than running from when the command first entered pending: it bounds how long the command waits for the speaker, and an absolute window would cut a conversation off mid-answer — the default 5 s would otherwise have to cover every utterance of a multi-slot exchange plus a `bufferWindow` each. What still bounds a stalled pending is silence, since the first unanswered window ends it. The confirmation re-entry restarts on the same rule, so a command filled slot-by-slot does not arrive at its confirmation stage with less time to confirm than one that was complete when first heard. Session logs gain a matching entry, `still pending (partial: unfilled [...])` with `accepted: false`, alongside the existing accepted follow-up entry. The two firing exits behind default-off opt-ins are unchanged and deliberate — confirming a partial match, and `FireAsIs` on timeout — and are now stated as such in `Documentation~/command-recognition.md`, together with the precondition they share and the consequence handlers have to live with: **`allowPartialMatch` gates both**, since only a partial-match pending ever holds a command with a required slot absent (one awaiting confirmation was complete when it entered), so `FireAsIs` alone cannot fire an incomplete command — but set `allowPartialMatch` and that command's handler must tolerate every required slot being absent. The `OnCommandPending` reference entry also now records that one pending command raises the event once per fill rather than once in total. ([#77](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/77))

- A command missing a required argument no longer fires on the ordinary flush path. `TryEagerCommit` has refused that shape since [#66](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/66), but that guard covers only the opt-in eager path; the default path asserted score and confidence and nothing else, leaving completeness to the missed-slot penalty (`−1.0`) to enforce by arithmetic. It does not enforce it. On the shipped demo grammar "launch all missiles target" matches `launch`, `{?quantity}`, `{weapon}` and `target`, strands `{target}`, and scores `(1 + 1 + 1 + 1 − 1) / 5` = **exactly `0.60`** — the default `minScore` itself — so it cleared the gate and delivered `launch_weapon` with no `target`, a launch order with nothing to launch at. Two more elements of debt made it worse rather than better: the penalty sinks a candidate further the *shorter* the pattern, so longer patterns were the exposed ones, and [#65](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/65)'s reduced literal miss cost lifted a further band (eight elements with a dropped literal alongside the missed slot) over the gate. The condition is now stated rather than left to the numbers, and deliberately **independent of `minScore`**: a missing argument is a missing argument at any score. Where the command opted into `allowPartialMatch` it now reaches the pending/slot-fill path it was always meant to reach — previously unreachable for precisely these commands, since that path is entered only from *below* the gate, so scoring well was what disqualified a command from being completed properly. With the flag off (the default) the utterance is reported through `OnUnrecognisedSpeech` instead of firing incomplete. The same condition also governs whether a new utterance preempts a live pending command, which is the half that is easy to miss: an incomplete command no longer cancels one, since it would otherwise take a half-finished command away and put nothing in its place. **Scope is slots only.** A missed required *literal* still fires — the command is fully determined and every argument present, which is what #65's reduced miss cost exists to allow — and that includes the case where the dropped literal was the pattern's own discriminating last word, which remains a documented limitation in `KNOWN_LIMITATIONS.md`: on a final transcript, unlike at the eager gate, no rule can recover a word that is simply gone, and refusing there would mean firing nothing. `ParseInternal` is untouched and still reports slot-missing candidates, because dropping them there would also delete the only input the partial-match path has. `VoxrBatchTestRunner` applies the same condition, so batch results keep predicting runtime behaviour. ([#73](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/73))

- Eager flush no longer commits a pattern whose **trailing** required literal was never spoken — firing a command the speaker has not finished saying, and where a sibling pattern shares the prefix, firing the **wrong** one. This is the same hole [#66](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/66) closed for slots, one element class over, and it evades the gate for the identical reason: a miss consumes no token, so a pattern whose last elements were never spoken leaves the match end at the end of the buffer exactly as a pattern that genuinely finished there does. The whole-buffer condition is then satisfied *vacuously* by precisely the utterances still in progress. Neither index the parser tracks can tell the two apart. The shipped demo grammar carries the shape — `switch to weapons` and `switch to navigation` diverge only on their last word — so a speaker two words into "switch to navigation" presents a buffer both patterns match at `(1 + 1 − 0.5) / 3` = `0.50`, tying, and registration order picks `mode_weapons`. At three elements the default `minScore` of `0.60` is what refuses that today, by arithmetic rather than by rule; at **four** elements the arithmetic stops helping — a four-literal pattern missing its last word scores `(3 − 0.5) / 4` = **`0.625`**, over the gate, with every other eager condition satisfied. A verdict above `None` now additionally requires that **no required element sit after the last element that actually matched**. A *medial* miss is deliberately still allowed, which is why this is a tail test and not a ban on missed literals: "launch all missiles hotel one" drops the "target" function word yet fills every slot and still lands its final element on the buffer's last token, so nothing the speaker says next was owed to it and it commits early exactly as before. An omitted trailing *optional* is likewise not an unmatched tail. Only the eager gate is affected — scoring, selection, and `ParseInternal` are untouched, so these buffers remain ordinary parse results and simply wait the `bufferWindow` they would have waited before eager flush was enabled. ([#70](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/70))

- Eager flush no longer commits a command whose required slot was never filled — firing it with a missing argument, and truncating the utterance immediately before the words that would have supplied it. The gate asserted score, start position, end position, and confidence, but nothing asserted **completeness**; it relied on the missed-slot penalty (`−1.0`) to sink such candidates below `minScore`, which is emergent rather than enforced. At five elements with exactly one missed slot the arithmetic lands on `3.0 / 5` = **exactly `0.60`**, which passes the default gate — and the end-of-buffer condition, which looks like it would catch an unfilled trailing slot, cannot: a miss consumes no *recognised* token, so it never advances the match end past anything the pattern matched — and where it does carry that end over a trailing `[unk]` run, it only makes the condition pass more readily. Either way the pattern appears to span the whole buffer while still missing an argument. The shipped demo grammar hits this on two of its own patterns: "launch all missiles target" commits `launch_weapon` with no `target` one word before "hotel one" arrives, as does "fire all missiles at". A verdict above `None` now additionally requires every required slot in the winning pattern to have matched. Required *literals* stay exempt by design — a dropped function word ("launch all missiles hotel one", `0.70`) leaves the command fully determined with all its arguments present, so it must not block an eager commit. Only the eager gate is affected: scoring, selection, and `ParseInternal` are untouched, so a partial match is still a legitimate parse result there. What it reached after the full `bufferWindow` was *not* the pending-command path, as this entry originally claimed — that path is entered only from below `minScore` and only for a command that opted into `allowPartialMatch`, so a slot-missing candidate above the gate simply fired with its argument absent. That gap is the flush-path condition fixed under #73 above. Buffers that used to commit incomplete now simply wait the window they would have waited before eager flush was enabled. ([#66](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/66))

- A second `VoxrSpeechRecogniser` no longer silently shares — and then frees — the first one's native bridge. The bridge is file-scope C++ state whose ABI carries no handle (`g_model`, `g_recognizer`, `g_initialised` in `vosk_bridge.cpp`), so a process has exactly one bridge however many components reference it, but nothing on the managed side said so. `IsInitialised` was not backed by an instance field at all: it asked `vosk_bridge_is_initialised()`, i.e. whether *the process* had a bridge. So the second component's `InitialiseAsync()` early-returned on the first's success and discarded its own model path, sample rate, and AGC target with no error, and `ReleaseNativeResources()` called the unconditional `vosk_bridge_destroy()` — which `OnDestroy()` calls — so **either** component's destruction freed the other's recognizer and model, leaving the survivor reporting `IsInitialised == false` and calling into freed memory. In an additive-scene VR app that fires on ordinary scene unload, not just on quit; it is also what forced the PlayMode test assembly to be excluded from Android players in #55. The bridge now has a single explicit owner — whichever component initialises it, released when that component calls `ReleaseNativeResources()` or is destroyed — and the claim is taken synchronously before the first `await`, so two `InitialiseAsync()` calls in the same frame cannot both get past the check. `IsInitialised` and `IsRecognising` are backed by that ownership rather than by the process, which is what the issue asked for: a component that initialised nothing now reports `false` whatever the bridge is doing, so it can no longer be handed the owner's configuration by the `if (IsInitialised) return;` early-out. Because an `async` continuation outlives the component that started it, the claim is re-checked after each `await` in `InitialiseAsync` — a destroy or a `ReleaseNativeResources()` landing during model extraction hands the claim away, and finishing the initialise anyway would leave the bridge initialised with *no* owner, the one state in which none of these guards can fire. Every other instance is inert towards the bridge rather than sharing it: `StopRecognition()` becomes a no-op, `ReleaseNativeResources()` still frees that component's own editor-backend resources but never calls the handle-less `vosk_bridge_destroy()`, so a duplicate's `OnDestroy` cannot free the owner's state, and `InitialiseAsync()`, `SetGrammar()`, and `ResetRecogniser()` fail loudly — `Debug.LogError` **and** `OnError` with `AlreadyInitialised`, naming the owning GameObject, since a developer who never subscribed to `OnError` was exactly who the silent version stranded. A failed initialise releases the claim, so one component's bad model path cannot lock out a sibling, and a destroyed owner's claim lapses even if its `OnDestroy` never ran. **A single recogniser is entirely unaffected** — the guards engage only once a second live instance exists. They are applied on every platform, including the Windows Editor, whose `EditorMicBackend` is per-instance and could in fact have run two recognisers side by side: a scene that works in the Editor and silently corrupts on device is harder to diagnose than one that fails identically in both, and enforcing on the Editor branch is also what makes the constraint testable, since the automated coverage runs in EditMode/PlayMode rather than on device. The constraint is now documented in `api/speech-recogniser.md` (including that `Initialise()` and `StartRecognition()` inherit the rejection, reported once per push-to-talk press), the getting-started lifecycle section, and `KNOWN_LIMITATIONS.md`, with the persistent-recogniser pattern to use instead of one per scene. Managed side only; the native ABI is unchanged, so refcounting the bridge or giving it a per-instance handle — which would let two recognisers genuinely coexist — remain open. ([#57](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/57))

- A leading run of `[unk]` no longer disables eager flush, so a politely addressed command ("Helm, coast") commits as fast as the bare one instead of always paying the full `bufferWindow` — 2.0s of dead air on Quest 3. `TryEagerCommit` required the winning match to begin at token 0, so any out-of-grammar preamble VOSK reported as `[unk]` pushed the match start past 0 and forced the verdict to `None`; `prefixHoldSeconds` was no help either, since that shortened hold only arms on the `HoldExtendable` verdict. The whole-buffer gate now measures from the first *recognised* token: a leading `[unk]` run is skipped, and the match must still consume everything through the end of the buffer. Trailing leftovers are unchanged and still block — recognised or `[unk]`, a tail is an in-progress utterance more speech could still complete, which is the whole-buffer rule's own rationale — whereas nothing arriving later can extend an utterance leftward, so the leading run carries no such ambiguity, and the sliding start already absorbs it for free everywhere else (`[unk]` is never charged by the skipped-word penalty and never counted in confidence). This only widens which buffers reach a verdict; scoring, selection, and the eager-eligibility analysis are untouched, and a leading word VOSK *did* resolve still blocks the commit exactly as before. Addressed forms of prefix commands now also reach `HoldExtendable` rather than `None`, so they arm the shortened `prefixHoldSeconds` hold where they previously waited out the full window. ([#43](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/43))

- When two patterns tie on match score, the parser now prefers the one that consumes more of the utterance, instead of keeping whichever the command asset happened to list first. Selection ran earliest start → highest score → most matched literals, with no term for the consumed span, so a command carrying both a bare pattern and a tailed sibling (`intercept track {track}` and `intercept track {track} {burn_level}`) tied at 1.0 with equal literal counts on an utterance that carried the tail. The tie fell through to registration order: if the bare pattern was listed first it won, and sequential extraction then matched the orphaned tail as a *separate* command — one spoken order silently delivered as two, with no warning and both marked successful, which defeats any policy the game applies at the command level. Array order in the asset was effectively load-bearing for correctness, and the workaround (listing patterns longest-first) collided with content keyed on `MatchedPatternIndex`. **Check your grammars for this:** the span term sits above the literal-count tie-break, so it decides more than the order-dependent ties it was added for — any two candidates that start at the same token and score equally now resolve by span, *including* pairs that literal count previously decided on its own, deterministically, whichever order they were declared in. A pattern with fewer literals but wider coverage now wins where it used to lose (`fire at {target}` over `fire at hotel` on "fire at hotel one"), and because the comparison runs across the whole command list this can change which **intent** fires, not just which pattern index (`go {place}` over `go {dir}` on "go north pole"). Grammars whose equal-scoring candidates always agree on span and literal count are unaffected. The span is measured over tokens a pattern actually matched, so a trailing `[unk]` cannot win a tie by being absorbed; literal count remains the next tie-break and registration order the final deterministic fallback. The same ordering is applied in the eager-flush scan, so the eager verdict still names the command a subsequent flush will fire — a tailed utterance that used to stop short of the buffer end now commits early instead of paying the full `bufferWindow`, and where the newly-preferred pattern is itself a prefix of a longer sibling the buffer now reports a complete-but-extendable match, which arms the shortened `prefixHoldSeconds` hold rather than the full window. ([#41](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/41))

## [1.4.0] - 2026-07-28

### Added

- `prefixHoldSeconds` on `VoxrCommandRecogniser` — a separate, shorter hold for the "complete match, but still extendable" state under `eagerFlushOnCompleteMatch`. Eager flush deliberately refuses to commit a command that is a prefix of a longer one (`orient to heading {heading}` prefixes `orient to heading {heading} mark {mark_sign} {mark}`) or whose trailing slot could still grow, so the common plain form paid the *entire* buffer window — 2.0s of dead air on Quest 3 — for an ambiguity a continuing speaker resolves almost immediately. The refusal to commit early is correct and unchanged; what changes is how long the buffer then waits for that continuation. When `prefixHoldSeconds` is above 0, a held complete match flushes after that much silence instead of the full `bufferWindow`, so the plain form fires in ~0.5–0.8s while the extended form stays speakable. The hold only ever shortens the wait — values above `bufferWindow` are ignored — and it applies solely to a buffer that already parses as one complete, confident, whole-buffer command: partial speech mid-split-command, unmatched speech, and grammars too complex for the eager precompute to analyse all keep the full window. The verdict is re-derived on every VOSK result, so a continuation that arrives restores the full window for the rest of the utterance. Default `0` keeps the previous behaviour exactly. ([#32](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/32))

### Changed

- The eager-flush eligibility analysis now consults slot vocabularies when deciding whether a pattern could be the opening of a longer one, instead of treating every slot position as compatible with anything. The old rule made a bare single-slot pattern (`{burn_level}`) a potential prefix of *every* longer pattern in the grammar — slot-vs-`close`, slot-vs-`intercept`, slot-vs-`decelerate` all counted as compatible — so a lone "coast" or "hard burn" paid the entire `bufferWindow` for an ambiguity that never existed. A slot facing a literal is now compatible only when some surface form of the slot actually begins with that word (a number sequence, only when the word is a digit word), so those patterns become eager-committable with no grammar change. Genuine holds are untouched: `decelerate` still waits for `decelerate {burn_level}`, and a value that really does start a longer pattern — `hard burn` against `hard burn now` — still holds. The vocabulary test is applied only where both patterns have provably consumed the same words (through their shared leading literals and the first element past them); past an earlier slot, which may have absorbed a different number of words on each side, the analysis stays conservative as before. Eager flush is still opt-in via `eagerFlushOnCompleteMatch`, and nothing changes when it is off. ([#33](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/33))
- Words the parser's sliding start skips before a match now count against the match score, so a stray utterance whose tail resembles a short pattern can no longer execute it. Previously the skipped words were free: an out-of-vocabulary word snapped by VOSK onto an in-grammar one ("thrusters port" heard as "thrusters report") let the parser skip the unmatched leading word and match a lone one-word pattern at a full 1.0, and a mid-order stumble ("half closure three clicks on track") could fire the command buried in the middle of it. Both cases were observed in-headset. Each skipped in-grammar word is now added to the score denominator, weighted by the new `skippedWordPenalty` field on `VoxrCommandRecogniser` (default `1.0`), which makes the score the fraction of the utterance the pattern actually covers — a one-element pattern reached past one skipped word scores 0.5 and is rejected by the default `minScore` of 0.6, while a five-element pattern reached past the same skipped word scores 0.83 and still fires. The penalty is proportional, so it only bites patterns short enough to be swallowed whole by a stray sentence; longer commands still absorb false starts. `[unk]` tokens are never charged — tolerating out-of-grammar preamble and hesitation is what the sliding start is for — and counting restarts after each extracted command, so chained commands in one utterance do not penalise each other. Set `skippedWordPenalty` to `0` for the previous behaviour. `VoxrBatchTestRunner` takes the same value as an optional constructor argument so batch results keep predicting runtime behaviour. ([#31](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/31))

### Fixed

- The `bufferWindow` Inspector tooltip recommended 1.5s on Quest 3 where every other source — `KNOWN_LIMITATIONS.md`, the README, the command-recognition and troubleshooting guides, and the command-recognition sample — recommends 2.0s. 1.5s sits below the ~1.9–2.1s inter-result gap measured on Quest 3, so the tooltip was recommending a window the project's own test matrices found insufficient; it appears to be a fossil of the v2.3 default rather than a Quest figure. The tooltip now says 2.0s and carries the measured gap plus the ~2.5s ceiling past which unrelated utterances start merging. Tooltip text only — no behaviour change, and the default remains 0.5s. ([#34](https://github.com/jinwoo1601/VoXR-Speech-Recognition/issues/34))
